# ADR 0015: Data-plane I/O: non-blocking USB transmit, bounded USB receive, DERP TCP window

Status: accepted for on-board validation, 2026-10-05; section A2 (elastic buffering) added after the first board run, same day. Numbered 0015 because PR #31 takes 0014. Follows ADR 0013 and `docs/research/forwarding-latency.md` (R4). Throughput effects are predictions until the plan at the end is run; the one board measurement that motivated A2 is quoted below.

## Context

Tunnel-to-USB traffic ran at about 0.5 Mbit/s against about 1 Mbit/s the other way, and a relayed (DERP) connection could not exceed about 0.7-1.3 Mbit/s at 36-64 ms round trip.

**USB transmit.** `usb_tx` (gateway_main.c) is the lwIP netif output for the USB interface. It runs in whoever holds the lwIP core lock: the tcpip task, or the WireGuard manager delivering a decrypted packet. It did `malloc` + `memcpy` and then `tinyusb_net_send_sync(..., 50 ms)`, which waits for the TinyUSB task to take the frame. Two waits are hidden in that call:

1. The sync call itself, up to 50 ms, whenever all NCM transmit blocks (NTBs) are in flight to the host.
2. `usbd_defer_func()` from a task is `xQueueSendToBack(..., UINT32_MAX)` in TinyUSB's OSAL (`osal_freertos.h`). When the TinyUSB event queue (16 entries, shared with USB interrupts) is full, it blocks forever, with the core lock held.

The same lock serves Wi-Fi RX delivery, NAT, the router and every socket, so a USB stall is an IP-stack stall.

**What the board showed (diagnostics build at cc72801, 15 s `iperf3 -R`, tunnel to USB, 0.63 Mbit/s).** The sender's TCP retransmitted 189 segments; `usb.tx_dropped_full` rose by 180 and `tx_ntb_blocked` by only 3; no router or WireGuard drops. So the loss was the transmit ring being full, not the USB endpoint being stuck: a ring of three frames (4,576 B) plus two 3,200 B NTBs cannot hold a TCP burst that arrives at Wi-Fi speed and leaves at USB speed. Upload (host to tunnel) was fine at 1.6-1.7 Mbit/s with about no retransmits. Memory was the reason the ring was small: release boot free heap is about 128.6 KB against a first-membership admission requirement of 103,448 B (about 25 KB margin), steady free with one tailnet is 71-78 KB, and a second tailnet must remain admissible. Section A2 resolves this with buffering that grows into spare heap and is returned before admission.

**USB receive.** `usb_rx` copies each host frame out of the NTB with `malloc`; lwIP frees it later. Nothing bounded the number of copies: they queue behind the tcpip mailbox (32 entries) and the router queue, 1.5 KB each, exactly when the heap is smallest.

**TCP window.** lwIP's receive window is `TCP_WND` = 5,760 B (4 segments of 1,440 B), no window scaling, send buffer the same. One connection can move at most one window per round trip: 5,760 B / 64 ms = 0.72 Mbit/s, 5,760 B / 36 ms = 1.28 Mbit/s. This matches the measured DERP numbers.

## Decision

### A. Transmit ring (`tinyusb_net_tx_ring_send`)

The shared wrapper `components/esp_tinyusb/tinyusb_net.c` gains a second send contract beside `tinyusb_net_send_sync()`. The bridge (`main/bridge.c`) and `tdongle_l2` keep the sync call and their tests; they allocate nothing for the ring (it is created only by `tinyusb_net_tx_ring_start`, which only the gateway calls).

```
lwIP core lock holder                 usb_txq worker (prio 6)        TinyUSB task
tinyusb_net_tx_ring_send()
  reserve slab range   (lock)
  copy frame           (no lock)
  commit               (lock)
  xTaskNotifyGive(worker) ---------> wake: take PM lock, ring non-empty?
  return ESP_OK / ESP_ERR_NO_MEM       usbd_defer_func(do_drain) ---> tx_drain():
                                       (may block; holds no lock)       peek (lock); can_xmit; xmit (copies to NTB)
                                       grow / shrink / reap chunks      advance (lock)
                          every IN transfer completion (__wrap_netd_xfer_cb) ---> tx_drain() again
```

- **No wait for a task, no allocation under the lwIP lock.** The producer takes a critical section twice (reserve and commit a range of a slab), copies outside it, and does a task notification. It never allocates, frees, defers or logs.
- **One lock for bookkeeping, copies outside it.** The first version of this PR was a lock-free single-producer, single-consumer byte ring (`head` and `tail` with release/acquire), and its ADR text rejected "a lock around the ring" because the producer would hold a critical section across the memcpy. Elastic buffering needs a third party (the worker, or admission) to change which memory exists while both ends run, and a lock-free ring cannot hand a slab back or add one. So the bookkeeping (the FIFO of slabs, which slabs are free, per-chunk use counts, the queued-frame count) is now behind one `portMUX_TYPE` critical section whose sections hold a few dozen instructions and never a memcpy, malloc, free, log or task call, so the producer waits at most for another core to finish a few instructions, never for a task. The payload copies stay outside, protected by ownership: a slab range is written only by the producer between reserve and commit, read only by the consumer between peek and advance, and a slab that is in the FIFO is never freed. The host test mock makes the section a real mutex and asserts, from every mocked call (`heap_caps_malloc/free`, task notify, defer, delay, TinyUSB calls, `tud_ready`, log), that none runs inside it; it also asserts the producer does exactly two sections per accepted frame. TSan (below) checks the rest.
- **Slabs, not a byte ring.** Storage is a FIFO of 1,524 B slabs (one maximum record: `[len:2][gen:2][payload padded to 4]`). Records are packed into the newest slab and never straddle two, so a record is contiguous (the NTB copy is one `memcpy`, and the "second part" of the old wrapped copy is gone). A slab is sealed when the next record does not fit and a successor is taken; the consumer frees a sealed slab as soon as its last record is in an NTB. For full-size frames capacity is exactly the slab count, like the byte ring (`n * 1524 + 4` for `n` frames); small frames pack many to a slab (68-byte records: 22 per slab), and a mid-size frame wastes at most the part of a slab it cannot fill (1,280-byte tunnel frames: one per slab, 240 B left, which a small frame can still use). When the queue runs empty the open slab is given back so the next frame starts in the lowest slab.
- **Exactly-once.** A record is consumed once: the copy into the NTB is synchronous inside `tud_network_xmit()`, then `advance` moves the read offset (the single release of that record). The ring owns its copy, so there is nothing for the caller to free and `free_tx_buffer` is not called for ring frames (a `ring` flag on the packet keeps the sync path's callback contract, including the v122 fix 505b08e, untouched). A stale or duplicate drain finds nothing to do. A flush (teardown) that runs between `peek` and `advance` moves the read offset; `advance` notices and does nothing, and the flush does not count the record the consumer is copying (the consumer counts it as sent or flushed). The slab being read is never freed under the consumer.
- **Link loss.** Each record carries the link generation current when it was queued. The generation is bumped the first time the producer, the worker, or `tinyusb_net_tx_ring_link_down()` (called from the gateway's `TINYUSB_EVENT_DETACHED`) finds USB not ready, so frames queued before a cable pull are discarded by the next drain instead of being delivered to the next host; a drain that finds USB not ready also discards. Frames stuck behind a link that went away without any event and with no traffic are found by the worker, which polls the link every 200 ms, but only while frames are queued (see "Polling" below).
- **Drain triggers.** The worker sleeps until a producer commits, then asks TinyUSB to run `do_drain`. When every NTB is in flight the drain stops and the frame stays queued; the NCM driver's IN transfer-complete handler (`netd_xfer_cb`, wrapped with the linker flag `-Wl,--wrap=netd_xfer_cb` in `components/esp_tinyusb/CMakeLists.txt`) drains again, in the TinyUSB task, right after the finished NTB returned to the free list. An in-flight NTB always completes, so a frame cannot be forgotten. **Polling:** the worker has no timer in the steady state (`portMAX_DELAY`). It has a 200 ms wait only while frames are queued, to notice a silent link loss and release the CPU-frequency lock, and a 500 ms wait only while elastic chunks exist, for the idle check. It never re-drains on a timer while the link is up: the first version polled once per tick and raced.
- **Backpressure and drops, all counted** (serial `memory` report, kind `usb`): `tx_dropped_full` (no free slab and no room in the open one: the new frame is dropped, TCP sees ordinary loss), `tx_dropped_link_down`, `tx_dropped_invalid` (length outside 14..1518), `tx_flushed_link_down`, `tx_ntb_blocked`, `tx_xfer_events`, `tx_worker_stack_free`, `tx_high_water` (bytes) and `tx_high_water_slabs`, `tx_sent`, plus the elastic counters in A2.
- **Why a worker task** and not `usbd_defer_func` from the producer: `usbd_defer_func()` from a task is `xQueueSendToBack(..., UINT32_MAX)` in TinyUSB's OSAL, which blocks forever when TinyUSB's event queue is full, with the core lock held. The `in_isr = true` variant is non-blocking but ISR-only. Priority and core (`gateway.h`, asserted in `gateway_main.c`): `usb_txq` is `GATEWAY_TASK_USB_TX_PRIO` 6 on `GATEWAY_TASK_USB_TX_CORE` 1, the TinyUSB task's core, so its defer wakes a task on its own core. On core 1 the order is usb_routes 8 > wg_mgr 7 > usb_txq 6 > TinyUSB 5 = coord 5. Cost: one task, 1,536 B of stack plus a 340 B TCB. The worker now also does the heap work of A2 (allocate, free, a few heap queries); none of it is on the packet path.
- **Why tail-drop** and not drop-oldest: only the consumer may release records, tail-drop is the right signal for TCP (loss of the newest segment) and keeps frames in order.

**Worker stack: 1,536 B.** The worker's deepest path was `tx_worker` -> `usbd_defer_func` -> queue calls, about 210 B of frames plus one Xtensa interrupt frame. It now also calls `heap_caps_malloc`/`heap_caps_free` (TLSF, a few hundred bytes of frames), `esp_pm_lock_acquire` and the gate callback (`ml_neg_busy`, one mutex). Not measured on the board; `tx_worker_stack_free` reports the real number, and the plan below says what to do if it is under 768 B.

### A2. Elastic buffering: grow into spare heap under bursts, give it back before admission

**Capacity.** Three slabs (frames) are permanent: one 4,572 B allocation at USB start, 4 B less than the 4,576 B byte ring it replaces, so the admission margin is not touched by the buffer itself. On top of that the worker adds up to 10 chunks of 2 slabs (3,048 B each, one heap block each): 3 + 10 x 2 = **23 frames, 35,052 B** at the cap.

**Why 23 (arithmetic).** A burst of `B` bytes arrives at the Wi-Fi ingress rate `r_in` and leaves at the USB rate `r_out`. Take `r_in` = 20 Mbit/s (a conservative TCP rate for a 1x1 11n station; an assumption, not a measurement) and `r_out` = 7 Mbit/s (875 B/ms, the USB full-speed ceiling in this ADR's earlier measurements). Fraction queued at the end of the burst: 1 - 7/20 = 0.65. A ring of `C` bytes absorbs a burst of `C / 0.65`:

| Frames | Ring | Burst absorbed | TCP segments of 1,420 B |
|---|---|---|---|
| 3 (before) | 4,572 B | 7.0 KB | 5 |
| 16 | 24,384 B | 37.5 KB | 26 |
| **23 (cap)** | **35,052 B** | **53.9 KB** | **38** |
| 24 | 36,576 B | 56.3 KB | 40 |

The board's 180 drops in 15 s with an average of 0.63 Mbit/s say bursts above 5 segments are routine; a sender in slow start or ACK-clocked at its congestion window sends a window per round trip, so a ring that holds 38 segments covers windows up to about 54 KB. Delay cost: a full ring is 23 x 1.5 KB / 875 B/ms = 39 ms of USB time, well under TCP's 200 ms minimum timeout and small against the tunnel's own round trip. Beyond the cap, tail drop is what TCP needs to slow down. 16 would absorb 37 KB and cost 21 KB less heap; 24 adds one frame. The cap is `GATEWAY_USB_TX_MAX_CHUNKS` (compile-time asserted to be 16-24 frames and at most 32 KB); tune it from `tx_dropped_full` against `tx_high_water_slabs`.

**Growth: only the worker allocates, only under pressure, only above floors.**

- The producer notes pressure when at most one free slab remains (so light traffic, which uses one slab, never grows) or when it had to drop, and notifies the worker.
- The worker grows only if all hold: the gate is open (below); the largest free internal block is at least `floor_largest` (`ML_ADM_LARGEST_BLOCK`, 24,000 B) before the allocation; free internal heap after the chunk (and a 16 B allocator header) stays at least `floor_free` = `ML_ADM_RECOVERY_BYTES + ML_ADM_NEG_PEAK_BYTES` = 32,384 B (the recovery reserve plus one negotiation peak, the two things a join in progress and HTTP recovery cannot do without); and, after the allocation, the largest free block is still at least `floor_largest`. A chunk that is the allocation that takes the largest block below the floor is freed again. This is the rule `ml_adm_slot_alloc_ok()` applies to WireGuard peer slots, applied here; all chunks are the same size (3,048 B), so a freed chunk returns exactly the hole it came from and the buffer does not walk the heap's free-block sizes. Each refusal is counted by cause and the next attempt waits 100 ms, so a burst of pressure cannot hammer the allocator. Cost of the two largest-block queries per chunk: IDF's `heap_caps_get_largest_free_block()` walks the heap's blocks inside the heap lock (the same call admission and the WireGuard slot check already make), a few tens of microseconds on this heap by estimate, once before and once after each of at most 10 chunks per burst, in the worker, never in the producer; the board plan checks `locks` and Wi-Fi drops during a download.
- It never allocates under the lock. The allocation is outside the critical section; publishing the chunk is a short section.
- Chunks are not larger because each is a single block that must find a hole (3 KB is smaller than the 6 KB frames of the old NTBs and than most live blocks); not smaller because each chunk costs one allocation and a table entry.

**Why the floor leaves growth enough room at steady state.** The elastic part is at most 10 x (3,048 + 16) = 30,640 B. Steady free heap with one tailnet is 71-78 KB, so the worst case is 71 - 30.6 = 40.4 KB free, 8 KB above the 32,384 B floor: growth is never refused by the floor at steady state with one tailnet, and a growth is refused once free heap is below 35.4 KB.

**Returning it: three triggers, frames in flight are never freed.**

1. *Idle.* A chunk none of whose slabs is in the queue for `idle_ms` (the component default is 2,000 ms; the gateway sets 10,000 ms, measured from the last slab released) is freed by the worker's housekeeping, one chunk per 500 ms pass, highest index first. The long period and the staging are the fragmentation hysteresis: bursty traffic with gaps shorter than `idle_ms` keeps its chunks and never cycles the heap (the 2 s default would free and re-allocate up to ten 3,048 B blocks per burst on a 5 s rhythm), and a quiet spell returns them one at a time. Admission never waits for this: reclaim (2) frees everything at once, so holding memory for 10 s costs admission nothing; growth stays behind the free-heap and largest-block floors, which a held chunk does not move. Slabs are taken lowest index first (the permanent slabs, then chunk 0, 1, ...), so under light load the high chunks go idle first and the buffer shrinks to what the load uses; an empty open slab does not pin its chunk (it is released when the queue is empty).
2. *Admission.* `start_member` takes the negotiation token (ADR 0013) and then calls `tinyusb_net_tx_elastic_reclaim(150 ms)` BEFORE measuring free heap. It retires every chunk: idle ones are freed at once; chunks that still hold queued frames stop receiving new frames and are freed when the last frame in them has been handed to USB; the call waits up to 150 ms for that (a full ring drains in 39 ms; `_Static_assert` requires three times that). It bumps an epoch, so a growth that had already passed its checks and allocated when the reclaim started is discarded (`tx_grow_raced`). While the token is held the gate is closed, so nothing grows again. If a stalled host leaves a chunk draining at the end of the wait, admission measures conservatively (less free heap) and the refusal is retried by the manager after ten seconds, as for any refusal.
3. *Negotiation phases.* The gate is `ml_neg_busy(ml_rt_negotiation())`: true while any membership holds the token, whichever phase (start, control, DERP). `ml_negotiation` gained an observer called on every free/held transition (grant, release, lease expiry; tested in `test_negotiation.c`); the gateway uses it only to wake the worker, which then retires idle chunks and stops growing. So the elastic part is gone, or draining, whenever a join is allocating its peak. Cost: during the seconds of a join, bursts see the three permanent frames again.

A chunk is freed only when none of its slabs is in the queue, and the slab the consumer is copying out of stays in the queue until the consumer advanced, so there is no free under a reader. `test_net_ring_cases` runs a reclaim and a teardown from inside the NTB copy of a frame that lives in a chunk, with memory poisoned on free and ASan on.

**CPU frequency (`CONFIG_PM_ENABLE`).** An `ESP_PM_CPU_FREQ_MAX` lock is held while frames are queued, so dynamic frequency scaling cannot slow the drain, and is released when the queue empties. It compiles to nothing when PM is off. The producer only commits and notifies (the commit sets `pm_want = true` inside the lock; the consumer, flush and teardown clear it inside the lock when the last queued frame goes). Only the worker acquires and releases, reconciling the lock with `pm_want` after every wake-up, so acquire and release cannot interleave; both edges of `pm_want` wake the worker. Link-loss flush, reclaim and teardown are covered: the flush empties the queue (edge), reclaim never touches the lock, and `tinyusb_net_deinit()` discards, retires and wakes the worker. The host test's PM mock asserts the lock is never acquired twice or released while not held, never inside the critical section or in the producer, and that after every worker wake-up it is held exactly while frames are queued.

**Counters** (kind `usb`): `tx_ring_bytes` (capacity now), `tx_ring_base_bytes`, `tx_ring_max_bytes`, `tx_elastic_held_bytes` (includes chunks still draining), `tx_elastic_chunks`, `tx_grow_events`, `tx_shrink_events` (idle), `tx_reclaim_events` and `tx_reclaimed_chunks` (admission/negotiation), `tx_grow_denied_{gate,heap,largest,nomem}`, `tx_grow_raced`, `tx_high_water` and `tx_high_water_slabs`, `tx_pm_{acquired,released,held}`.

### B. Bounded receive (`usb_rx_budget.h`)

`usb_rx` admits at most 22 frames in flight between the NTB copy and lwIP's free (`usb_free_rx`). Over the cap, the frame is dropped and counted (`rx_dropped_busy`). Frames outside 14..1518 bytes are rejected before the allocation (`rx_dropped_invalid`). A slot is released exactly once: from `usb_free_rx`, which esp_netif calls on every path (checked against `ethernetif_input` in IDF v5.5.5: no interface, interface down, `esp_pbuf_allocate` failure and `netif->input` failure each free the buffer through the driver exactly once), or directly when `malloc` fails before the copy is handed over. `tud_network_recv_cb` ignores `usb_rx`'s result and always renews, so a refused frame cannot stall the NCM receive path. This replaces an effectively unbounded queue (tcpip mailbox 32 + router) with a bound that is visible in the report.

**Interplay with the router queue (PR #31).** The router queues the lwIP pbuf that wraps the `usb_rx` copy (`gateway_host_input`), so every packet in its queue (`ROUTE_QUEUE_DEPTH` 16) or hold list (`ROUTE_HOLD_SLOTS` 2) keeps its receive slot until `usb_routes` frees it. The two budgets therefore count the same frames and answer different questions: the router's byte budget (`rt_queue_budget`: free heap above the 16,384 B recovery reserve, at most 16 KB, floor two packets) shrinks with the heap; the receive cap is a fixed ceiling that does not. With the first version's cap of 12, a congested router could hold 12 of 12 slots and drop DHCP, DNS, ARP and setup HTTP, the traffic the recovery reserve exists for. The cap is now `ROUTE_QUEUE_DEPTH + ROUTE_HOLD_SLOTS + 4` = 22 (asserted in `gateway_main.c`): the router can fill its own limits and still leave four slots. Heap: the router's byte budget already bounds what it holds, so the extra slots add at most four frames (6 KB) transient, and only in a flood; the reserve is deliberately not applied to receive frames, because recovery traffic is what spends it. Admission (`ml_admission.h`) does not charge the receive frames or the ring; see below.

### C. NTB size: 3,200 B (was 6,400), count 2, to pay for the ring

Measured on the unified build (esp32s3, IDF 5.5.5), each extra IN NTB cost 6,408 B of DIRAM and the same in flash image (data buffers in `.data`). The first version of this ADR kept the NTBs and added the ring on top. That put about 8.7 KB on the heap before membership admission, whose margin on the release image is only about 4.6 KB (see Memory budget). The ring decouples the producer from the USB endpoint, so the NTBs no longer have to absorb producer bursts; they only have to keep the endpoint fed. So the two NTBs go back to esp_tinyusb's default of 3,200 B (the same size as the three OUT NTBs, two full frames each; Linux requires at least 2,048), and the 6,400 B this frees pays for the ring and its worker.

How big the ring is: it only has to hold what the producer adds between two drains. Drains happen at every IN completion, and an NTB of 3,200 B is on the wire for about 3.7 ms at the observed USB ceiling of 7 Mbit/s (875 B/ms), so one NTB period of a producer running flat out at that ceiling is about 3.2 KB. Three full frames (4,576 B) cover that with one frame to spare (this sizing covers only the NTB period; the first board run showed it does not cover TCP bursts, which is what A2 fixes); the on-board runs saw 0.5-1 Mbit/s, well below it. Every byte of the ring is therefore justified by "one NTB period at the USB ceiling", and the working total buffering is 3 frames (ring) + 2 x 2 frames (NTBs) = 7 frames, against the previous 8 frames in NTBs alone.

If the board shows `tx_dropped_full` with `tx_high_water` equal to `tx_ring_bytes`, raise the ring before touching the NTBs (A2: the ring is now elastic, so raise the cap, not the permanent part). If `tx_ntb_blocked` climbs while the ring stays below `tx_high_water`, the host is slow to take NTBs and more NTBs would help. `main/gateway_main.c` has `_Static_assert`s that keep `NTB count x size + ring + worker (1,536 + 340)` within `2 x 6,400 + 512` (the previous NTB memory plus 512 B), that an NTB holds two frames and that the permanent ring holds three. This is a decision from the memory cost and the USB arithmetic, not from a throughput measurement; the on-board plan below measures it.

**NTB size after the elastic change: stays 3,200 B (restoring 6,400 B considered).** *(ADR 0022: the 100-200 us endpoint-idle estimate below was wrong under load; the TinyUSB task ran behind wg_mgr and the drain was 2.6 Mbit/s. The fix is task priority, the NTB size stays; the priorities quoted in this ADR (usb_txq 6, TinyUSB 5) are superseded by 0022.)* Restoring the two IN NTBs to 6,400 B costs +6,400 B of static DIRAM that nothing can reclaim: it would move the admission margin from about 24.6 KB to about 18.2 KB and it counts against every later membership. What it would buy is aggregation, four frames per IN transfer instead of two. The endpoint is refilled from the transfer-complete handler, so between two transfers it idles only for that handler, about 100-200 us (an estimate, not a measurement) against 3.7 ms of wire time per 3,200 B NTB: roughly 3-5% of the USB ceiling, and the extra buffering is not what removes the loss (the ring is). So the permanent, unreclaimable memory goes to nothing, and the decision is gated on a measurement: if after A2 `tx_dropped_full` is about 0 and the download is still well under the USB ceiling while `tx_ntb_blocked` grows, try `CONFIG_TINYUSB_NCM_IN_NTB_BUFF_MAX_SIZE=6400` (plan step 4).

Admission (`start_member`, ADR 0013 N1.2, `ml_admission.h`) requires `free >= required` and a 24,000 B largest block. | member growth: WG device 228 + 4 x 904 + TLS 1,336 + lwIP 9,300 + other 5,600 + 2 x 1,464 pending | 23,008 |

That is a margin of about 4,352 B. What this PR changes before admission, against the merged base (origin/overhaul/multi-tailnet 03002d8), both built with `idf.py size` on IDF v5.5.5:

This is thin: 28 B over the bar, from a boot figure measured on a different tree. The first version of this PR (6,144 B ring, 2,560 B stack, NTBs unchanged) was +9.1 KB heap and no static saving: a margin of about -4.7 KB, the only membership refused. If the board shows less margin than predicted, the ring can be cut to two frames (3,052 B, +1,524 B of margin) at the cost of one frame of burst absorption; correctness is the same. A separate change is expected to free about 50 KB of static D/IRAM, which makes the margin comfortable, so the ring stays at three frames rather than trading burst absorption for bytes. Assumptions: block headers at most 8 B; no other allocation changes (the TCP window and send buffer do not allocate until a socket uses them); `largest >= 24,000` is untouched by the static shrink and the 6.5 KB of heap comes out of the large boot region (read `largest` in the `admission` report).

| Flash code 859,612 -> 862,480; image 1,245,187 -> 1,248,071 | +2,868; +2,884 |

The elastic part itself is not in the boot heap and not a term of `required`: it exists only while the heap can afford it and is gone before the measurement (below). At the cap it holds 10 x 3,048 = 30,480 B plus allocator headers (about 30.6 KB).

**Admission proof (what is guaranteed, and by which test).**

1. *At the moment admission measures, the elastic buffer holds nothing it can give back.* `start_member` holds the token (gate closed), reclaims, then measures. Idle chunks are freed by the call; chunks with queued frames are freed as their frames leave, the call waits up to 150 ms (a full ring drains in 39 ms). Test: `test_reclaim_for_admission` grows to the cap with the NTBs blocked, reclaims, drains, and requires the mocked free heap to equal its value before any growth, the allocation count to be the permanent block only, and every frame to be delivered once, in order, intact. A variant sleeps in the reclaim while a "TinyUSB task" drains in the background; another times out (5 ms) and requires the held bytes to be reported, not hidden.
2. *Nothing grows between the gate check and the measurement.* The gate is closed while the token is held, and an epoch discards a growth that passed its checks before the reclaim and publishes after it. Tests: gate refusal before the allocation (no allocation attempted), gate closing during the allocation (chunk freed), reclaim during the allocation (`grow_raced`, chunk freed).
3. *Frames in flight are never freed.* A chunk is freed only when none of its slabs is queued, and the slab being copied out stays queued. Tests: reclaim, and separately teardown, issued from inside the NTB copy of a frame that lives in an elastic chunk (freed memory is poisoned and ASan is on); a reclaim with every chunk full of frames; frames delivered once, in order, bytes intact.
4. *Growth cannot starve a join or recovery.* Floors: free heap after the chunk at least 32,384 B (a negotiation peak plus the recovery reserve), largest block at least 24,000 B before and after. Tests: one byte short of the free floor is refused, exactly at the floor is allowed and the free heap never goes below it over 20 further attempts; largest block below the floor refused before allocating; an allocation that takes the largest block below the floor is undone; allocator failure; each counted by cause; refusals are rate limited.
5. *Idle shrink.* After 2,000 ms without a queued slab a chunk is freed (1,999 ms is not enough, 2,000 ms is), light load keeps only what it uses, frames in flight keep their chunk, an empty open slab does not pin a chunk.
6. *It does not make a second tailnet harder.* The second membership needs 21,196 + 23,008 + 16,000 + 16,384 + 2,800 = 79,388 B free (no shared runtime), against 71-78 KB steady free after the first on the board; that existing gap is independent of this change, and this change contributes 516 B of boot memory and nothing at the measurement.

Transient, not at admission: the send buffer doubles (5,760 -> 11,520 B), so a socket that uploads at full rate can hold four more queued segments. A queued segment is one `PBUF_RAM` pbuf (16 B header + 54 B link/IP/TCP headroom + 1,440 B payload, about 1.5 KB with the allocator header) plus a 20 B TCP segment record, so up to +6.2 KB per bulk-uploading socket: DERP is one per membership, and the setup HTTP server allows two sockets. Worst case +18.6 KB transient, on a board that has 44-66 KB free after one membership; it comes back when the data is acknowledged. The router queue's heap-aware budget (above) keeps draining its own share of that headroom first.

### D. TCP window: global 11,520 B (8 x MSS), send buffer the same, receive mailbox 10

What the IDF v5.5.5 lwIP supports (read in `components/lwip`):

- **Per-socket window: not available.** `LWIP_TCP_WND_DEFAULT`'s Kconfig help mentions `setsockopt(TCP_WINDOW)` and `TCP_SNDBUF`, but neither exists in the lwIP sources (`sockets.c`, `tcp.h`). `TCP_WND` is a compile-time constant, `TCP_WND_MAX(pcb)` is derived from it and `tcp_recved()` clamps to it, so a pcb cannot be given more. `SO_RCVBUF` is compiled out (`CONFIG_LWIP_SO_RCVBUF` unset) and in any case does not affect the TCP window. Making it per-pcb means patching the pinned IDF lwIP, which we do not carry.
- **Window scaling: not available and not needed.** `CONFIG_LWIP_WND_SCALE` depends on `SPIRAM_TRY_ALLOCATE_WIFI_LWIP`, and this board has no PSRAM. Any window below 65,536 B works without it, and we are far below that.

So the window is global, and the question is how large. Window memory is not reserved: lwIP's receive window is an advertised number. Memory is held only by segments that arrived and have not been read, and the data in flight in the network costs nothing. The real exposure is a stalled reader. With `CONFIG_LWIP_L2_TO_L3_COPY` off, queued TCP segments are pbufs that reference Wi-Fi RX buffers, so a stalled socket pins up to window/MSS of the 16 dynamic RX buffers (`CONFIG_ESP_WIFI_DYNAMIC_RX_BUFFER_NUM`). We therefore cap the window at half that pool:

| Window | Segments | Ceiling at 36 ms | at 64 ms | Pins at worst (one stalled socket) |
|---|---|---|---|---|
| 5,760 (before) | 4 | 1.28 Mbit/s | 0.72 | 4 of 16 RX buffers |
| **11,520 (chosen)** | **8** | **2.56** | **1.44** | **8 of 16** |
| 17,280 | 12 | 3.84 | 2.16 | 12 of 16: one stuck socket can starve Wi-Fi RX |

Companion changes, all in `sdkconfig.defaults`:

- `CONFIG_LWIP_TCP_RECVMBOX_SIZE` 6 -> 10 (window/MSS + 2, as the Kconfig says). With 6 the mailbox can fill before the window does when segments are small; lwIP then parks the data in `refused_data` and retries on its 250 ms timer instead of delivering it. The 10 entries only bound segments queued for the application, they do not allocate. Cost: 16 B per TCP socket.
- `CONFIG_LWIP_TCP_SND_BUF_DEFAULT` 5,760 -> 11,520. The send buffer holds unacknowledged copies, so this is real heap while a socket uploads at high rate: 8 queued segments per socket instead of 4. IDF builds lwIP with `MEMP_MEM_MALLOC = 1`, so the `MEMP_NUM_TCP_SEG` pool of 16 is only a default, not a limit: nothing caps the segments queued across all sockets except each socket's own send buffer (and `TCP_SND_QUEUELEN` = 4 x buffer/MSS = 32 segments per socket for tiny writes). The worst case is therefore per socket, summed over the sockets that send at once (see Memory budget).
- Setup, HTTP and DNS sockets are not given larger windows (they cannot be), but they do not use them: the HTTP server is limited to 2 open sockets (`max_open_sockets = 2`) and DNS is UDP. A reader that keeps up holds nothing.

Honest cost: no standing heap; transient heap of about 12.3 KB per bulk-uploading socket (6.2 KB more than before), and up to 8 Wi-Fi RX buffers (about 13 KB of dynamic heap, taken from the same 16-buffer cap that already bounds Wi-Fi) per stalled-reader socket. The "half the pool" rule is per socket, not aggregate: lwIP offers no cap across sockets, so four sockets that all stall with full windows (DERP, the control stream and two setup HTTP connections) could pin the whole pool, and the Wi-Fi driver then drops frames (counted, no crash). A reader that keeps up pins nothing, and every long-lived socket here has a task that reads continuously. The ceiling doubles; it does not lift the DERP path to the multi-Mbit/s that the egress changes may reach. Raising it further is a one-line change, but only with a larger Wi-Fi dynamic RX pool (each extra buffer is on-demand heap), and that trade should be made from the on-board numbers below.

`main/tcp_window_budget.h` makes the constraints build-time `_Static_assert`s in `gateway_main.c` (window below 64 KB without scaling, mailbox >= window/MSS + 2, window at most half the RX pool, send buffer within the default segment pool size, at least two segments). The last-but-one is a sanity bound on the lwIP default, not a heap limit (see above). `tools/test-tcp-window.py` compiles the same header against the values parsed from `sdkconfig.defaults` and proves each assertion is live by compiling five wrong configurations and requiring a failure.

## Rejected

- **A larger global window (12+ segments) now.** One stalled socket could pin most of the Wi-Fi RX pool, and the send side grows the same way. Revisit with on-board numbers.
- **Patching lwIP for per-pcb windows** (to give only DERP sockets more). The accounting above shows the cost is in the stalled-reader case, which a per-socket option would not remove for DERP itself; the patch would diverge from the pinned IDF.
- **A static pool of preallocated RX frames** for `usb_rx`. 12 x 1.5 KB of standing memory against a transient bound with the same limit.
- **Drop-oldest transmit** (needs the producer to move the read side).
- **A critical section around the payload copy** (the producer would mask interrupts for a 1.5 KB memcpy): the lock in A covers bookkeeping only.
- **More or larger NTBs** instead of a ring: 6.4 KB each at the old size, and they do nothing for the producer-side wait.
- **A ring on top of the unchanged 2 x 6,400 B NTBs** (the first version of this PR): +8.7 KB of heap before admission against a 4.6 KB margin.
- **A fixed 23-frame ring**: 30.6 KB of standing memory against a 25 KB admission margin, and no second tailnet.
- **Growing from the producer** (`malloc` in `usb_tx` with failure meaning drop): allocation and its heap lock under the lwIP lock, the thing ADR 0015 exists to remove.
- **Keeping the lock-free SPSC byte ring and adding elasticity to it**: growth by the producer is the line above; growth by another thread needs the ring to be wrapped-safe to extend (only when `head >= tail`, with consumer and producer agreeing on the capacity in force), and returning memory to admission while idle needs a third party to take slabs out from under both ends. All of those are a lock in disguise with weaker tests.
- **Freeing chunks from the TinyUSB task** (the consumer finding a retired chunk empty): the consumer only wakes the worker; the heap work stays in one place, out of the USB path.
- **Restoring 6,400 B IN NTBs** now: see C; unreclaimable standing memory for an estimated 3-5%.
- **Kicking TinyUSB from the producer** with `usbd_defer_func(..., in_isr = true)`: non-blocking, but an ISR-only API.
- **Polling from the worker while NTBs are busy**: a tick-rate wakeup that was also racy (see A). The IN transfer-complete event replaces it.

## Consequences

- `usb_tx` can no longer hold the core lock, so USB stalls stop being IP-stack stalls. They become counted ring drops.
- The tunnel-to-USB path costs one copy (into the ring) and one copy (into the NTB), and no `malloc`/`free` per packet.
- Standing memory: a 4,572 B permanent ring and one task (1,536 B stack + 340 B TCB), paid for by the IN NTBs going from 6,400 to 3,200 B (net +228 B of boot heap against the previous base, Memory budget), and 516 B less boot heap than the base of the elastic change (568 B of bookkeeping). Elastic memory: up to about 30.6 KB while a burst needs it and the heap can afford it, none while a membership is being admitted or negotiated.
- Each IN NTB carries at most two full frames; the ring, which grows to 23 frames, is what absorbs bursts.
- During a join (token held, seconds) the buffer is the three permanent frames again; bursts in that window are dropped as before this change.
- The ring bookkeeping is behind a short critical section, not lock-free. `usb_tx` can wait for another core to finish a few instructions, never for a task.
- The USB wrapper depends on `heap` (and `esp_pm` when `CONFIG_PM_ENABLE`).
- The legacy bridge image keeps 4 x 6,400 B NTBs (root `sdkconfig.defaults`) and does not start the ring. It links the same wrapper, so the `--wrap` is present there too and is a no-op when the ring is not started.
- Drops that were silent (`ESP_ERR_NO_MEM` from `malloc` or a 50 ms timeout) are now visible in the `usb` report.

## Invalidation

- `tx_dropped_full` stays high with `tx_ring_bytes` at the cap (35,052 B) and `tx_high_water_slabs` 23: the USB drain is slower than the producer for longer than a burst, not bursty; look at the TinyUSB task priority, endpoint rate and `tx_ntb_blocked` instead.
- `tx_grow_denied_largest` rising on a healthy heap: the chunk size does not suit the heap's free-block sizes; try chunks of one slab (set `TINYUSB_NET_TX_CHUNK_SLABS` to 1 and `TINYUSB_NET_TX_MAX_CHUNKS` to 24, so the slab table still totals 32).
- Admission margin below 24 KB at boot, or a refusal that `tx_elastic_held_bytes` explains: the reclaim wait (150 ms) is too short for this host's USB drain; raise `GATEWAY_USB_TX_RECLAIM_WAIT_MS` (and its assert).
- Wi-Fi RX buffer exhaustion or `memory` heap minimum below the admission floor after the window change: return to 5,760 B and treat the DERP read path (PR-A) as the lever.


### Review addendum (PR #37 review)

- **Heap walk cost.** `heap_caps_get_largest_free_block` walks the heap with the heap lock held. The worker now checks the O(1) free total first and walks only when the total already allows a chunk (twice per growth: before and after the allocation). A refusal backs off 100, 200, 400, 800, 1,600 ms (reset by a growth), so a sustained burst against a tight heap walks it at most about once a second.
- **Teardown.** `tinyusb_net_deinit` bumps the epoch, so a growth that allocated before the teardown cannot publish a chunk after it.
- **Producer.** The pressure test is `mask & (mask - 1) == 0` (at most one free slab) rather than a popcount, so no libgcc call runs inside the critical section.
- **One PM mechanism.** PR #35 (ADR 0016) is merged, so the ring has no power-management code of its own (no `esp_pm` dependency). `tinyusb_net_tx_config_t` carries `pm_begin`/`pm_end`/`pm_ctx`; the worker, the only caller, calls them on the empty/non-empty edges, strictly alternating, with no ring lock held. The gateway binds them to a `tdongle_pm_burst_t` registered as `usb_txq`, so the hold has the helper's depth accounting, forced release and `/status` counters. Without PM (legacy bridge, host builds) the helper holds nothing; a caller that passes NULL hooks gets no hold.
