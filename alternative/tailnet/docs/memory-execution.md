# Memory execution — all selected opportunities

Aim: reduce firmware RAM peaks and fragmentation while preserving usable, independent memberships, saved identities/Wi-Fi, and routing semantics. Scope includes DERP packet ownership, bounded setup JSON, control-send reuse, staged map parsing, and stack instrumentation. No physical flashing, merging or production publication. First hardware milestone is sustained traffic on one tailnet; then simultaneous traffic on multiple memberships.

## Execution checklist

- [x] DERP receives into the final owned packet allocation; fragmented reads, timeout, allocation failure and queue rejection must not corrupt or leak. Reject the tempting shortcut of handing consumers an interior pointer or transient shared buffer.
- [x] Setup responses use bounded serialization and short snapshot locking; slow/disconnected clients and concurrent membership removal must not retain locks, access freed clients or return partial successful JSON. Reject replacing heap pressure with long locks.
- [x] Control send path reuses bounded storage; partial writes, concurrent memberships, encryption failure and nonces remain correct. Reject sharing ciphertext without serialization or advancing nonces before failed encryption.
- [x] Maps produce bounded staged semantic updates without a full cJSON DOM; initial/incremental peers, authoritative omissions, removals, patches, preferred DERP and self identity remain equivalent. Invalid late input must apply nothing. Reject incremental mutation before validation and silently dropping capacity failures.
- [x] Expose per-task stack high-water measurements; reductions require board evidence across register/reconnect/traffic. No blind reductions from nominal allocation sizes.
- [x] Build pinned firmware and sanitizer suite, fresh diff review, package signed Android preview, verify assets/partition layout and serve it.

Critical assumptions: retained topology fits the declared bounded peer/DERP model; allocation savings contribute to actual peak headroom; hardware transport supports stable traffic. Model-checkable risks above require adversarial evidence. Runtime stack sufficiency, setup latency and real peer traffic are Accepted with rationale pending connected board measurements. Stop/pivot if semantics differ, unbounded allocation replaces a removed copy, capacity failures mutate routing, or hardware peaks invalidate the reserve. All improvements are selected; implementation order is risk containment, not a scope reduction.

## Delivered in firmware 0.2.5 / APK v109

- DERP packet receive has one payload allocation, with the sender key read separately. One deadline covers fragmented headers, key and payload; timeout/failed allocation reconnect rather than forwarding incomplete data. Non-packet control-frame dispatch remains unchanged.
- `/status` uses a 1312-byte snapshot per saved membership and a 256-byte serializer. Allocation occurs outside the lifetime lock; lock acquisition waits at most 20 ms per attempt. Sending holds no membership/client pointers or locks. Growth between count/copy, odd or changed peer-generation counters, and busy membership operations return HTTP503 with Retry-After. Client lifetime is protected by the membership lock; peer metadata consistency is checked against the peer owner's update generation. Global connection/heap counters remain point-in-time measurements, not an atomic snapshot of the entire device.
- Registration, initial map requests, long-poll requests and endpoint updates encrypt in their owned HTTP/2 buffer with explicit 16-byte MAC tailroom. Coordination tasks retain independent sockets, keys and nonces. Small acknowledgment sends retain the original bounded allocation path. Request construction still uses cJSON; no claim of allocation-free control traffic is made.
- Incoming maps validate incrementally and stage semantic changes. Only one projected record has a bounded nonallocating cJSON-compatible view; there is no whole-map JSON tree or whole retained-map output string. The existing semantic consumers decode the view into owned staged values. Registration and staging overlay the same aligned 24576-byte workspace. Compiled stage size is 23992 bytes; parser size is 5012 bytes (12 more than v108). The peer owner applies one admitted batch, handling authoritative omissions before additions so a full table can be replaced. Invalid late input, decoding/capacity errors, allocation failure and queue rejection cannot apply preceding staged changes.
- At most one map batch can be outstanding per membership. Admission waits at most one second for the prior batch, then fails explicitly without another allocation. The consumer releases the pending flag only after freeing the batch. This avoids multiplying payload memory by the 16-element pointer queue. Maximum committed batch is 24 updates (eight adds, eight removals, eight patches), 7208 bytes including the envelope. The stage also allows the eight changed entries that an authoritative full list supersedes.
- `/status` exposes `stack_free_bytes` for net_io, derp_tx, derp_rx, coord and wg_mgr. ESP-IDF's task.h specifies these high-water values in bytes. Missing/nonrunning handles report null. Android's existing automatic archive preserves the fields after USB unplug. **Stack reductions remain pending actual board measurements**, including reconnect and traffic; the 46 KiB nominal task-stack allocation is unchanged. Stack canary checking remains enabled.

Limits are explicit: raw map 1 MiB; nesting 32; encoded field names 128 bytes; scalar tokens 95 bytes; projected record 4095 bytes plus terminator; record view 128 nodes and 4096 decoded-string bytes; eight entries per peer update section; four DERP regions/two nodes per region. Duplicate consumed root fields and unrepresentable text (including embedded NUL or isolated surrogate) are rejected. These bounds replace implicit heap pressure with explicit errors; larger individual records/topologies remain unsupported. Preferred DERP retention, identity updates, expiry, authoritative/incremental peers, removals and patches are preserved within the bounds. Callback mode retains the earlier full-map DOM path and its bounded raw buffer; the gateway does not configure a callback.

Compiled membership context is 9216 bytes; startup admission baseline becomes 78348 bytes with the same provisional recovery reserve. This is accounting, not proof of actual peaks or supported membership count.

## HTTP/2 follow-up: firmware 0.2.6 / APK v110

The v109 automatic Android capture showed 134 failed map attempts, zero map bytes, HTTP/2 frame type 7 (GOAWAY), and approximately 90 KB free heap. This fails before semantic map parsing. Inspection found that the connection preface sent an unsolicited SETTINGS ACK while the registration reader also acknowledged received SETTINGS. A server can reject the extra acknowledgement as a protocol error; the old capture did not retain its numeric close reason, so that specific server reason remains unconfirmed.

Remove the unsolicited ACK, preserve HTTP/2 bytes following the length-delimited EarlyNoise message in the existing temporary h2_acc allocation, and let registration consume and acknowledge each received SETTINGS exactly once. Consume pending bytes before blocking for another Noise record; release them on consumption or connection close. Keep the streaming parser, bounded allocations, stack sizes, flash layout and saved identities unchanged. Registration and map diagnostics now retain numeric GOAWAY/RST_STREAM errors. Guard the connection-window subtraction against configurations smaller than the HTTP/2 default.

Adversarial host checks exercise proactive and delayed SETTINGS, one-byte fragmentation, repeated actual SETTINGS, received ACK frames, challenge extraction and preserved settings bytes, absence of unsolicited preface ACK, and numeric close reasons in both registration and map reads. ASan/UBSan and the complete firmware build/package are required before publishing. These checks reject both a blind ACK and the tempting removal that discards proactive settings. Real forwarding remains unverified until the user flashes this firmware and tries one membership with peer traffic; another GOAWAY should now identify its error code instead of masking it as a map-format failure.

## Hardware capture follow-up: Android v110 / firmware 0.2.6

On 2026-10-01 the Android v110 archive showed the earlier v0.2.5 failures as two map attempts ending in GOAWAY, zero map bytes, and `routing_ready=false`; the numeric close code was not available in that old firmware. The archive later observed v0.2.6 for four status samples, but the membership was IDLE with no map-attempt diagnostic. Repeated status requests then failed with `SocketException`; the membership was later disabled. The final root snapshot had no USB device attached. Therefore this capture does not confirm v0.2.6 routing, and no v0.2.6 map close reason was observed. Full findings and retrieval procedure are in `docs/diagnostics/v110-2026-10-01.md` in the Android repository; its raw archive remains local and uncommitted.

Retrieval constraint learned from this run: while Android is attached to the dongle via USB Ethernet, its phone-side debug URL may not be reachable from a computer on Wi-Fi. Automatic diagnostics remain on Android. Reproduce while attached, unplug, allow Android to return to Wi-Fi, then fetch the root URL or export Help → Diagnostics. Do not ask the user to leave the USB connection active while expecting remote retrieval. The capture also confirms Wi-Fi can be active while airplane mode is enabled; airplane mode alone is not evidence that Wi-Fi is unavailable.
